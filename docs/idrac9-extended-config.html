Known backend branches

  • GetRACExtendedConfig and SetRACExtendedConfig both contain selector/token tables rather than one opaque pass-through.
  • Selector 0x23 contains explicit IPv6 Enable/URL handling.
  • SetRACExtendedConfig contains RFS.1 and RFS.2 MediaAttachState transitions and reports enable/disable failures.
  • Attribute forms include integer, integer-list, string, and string-key paths with distinct length validation.

Why the backlog does not shrink

All three addresses remain in the global 123-address backlog. Reservation has decoded immediate transport semantics but still lacks channel/activation closure; Get/Set additionally lack a complete nested selector denominator and effect map.

  • The radare2 PDC evidence is structural corroboration, not source-equivalent decompilation.
  • The selector/token tables and every downstream attribute effect are not yet exhaustively partitioned.
  • No runnable codec or live-system claim is made.

Security follow-up · Unknown impact

CmdSetExtendedConfigure accepts any payload length >=9, but selector 0x02 license validation reads payload byte 22 and selector 0x12 reads payload byte 17 without a matching per-selector length check. BridgeMessage dispatches a 236-byte request object, so these are not allocation-overrun reads. KCSChannelReceiveMsg and IPMIIPCChannelReceiveMsg zero all 236 bytes before copying. In contrast, KCSPollingThread reuses one stack-resident request object inside its receive loop, copies only the declared payload, and never clears the object, so a longer KCS request can determine tail bytes later consumed by a shorter request. Exact KCSChannelInit code passes KCSPollingThread to pthread_create for each successfully initialized KCS channel, proving this is an intended receive path rather than dead code. ProcessCmcIpmiMsg likewise queues an object whose decoder writes only its header and declared payload without clearing its tail. BridgeMessage zeroes its separate 200-byte response object, so Get selector 0x02's pre-backend response-data byte 8 is zero and the meaningful Get check occurs after returned data is copied.

  • KCSChannelReceiveMsg: memset(request, 0, 236) before RawKCSRead; short-request tail is zero.
  • IPMIIPCChannelReceiveMsg: memset(request, 0, 236) before RawIPMIIPCRead; short-request tail is zero.
  • KCSPollingThread: one stack request object is reused across the polling loop without memset; only declared payload bytes are overwritten before queueing, making later short-request tail bytes stale and controllable by a prior longer request on that thread. KCSChannelInit passes this exact function to pthread_create for every successfully initialized KCS channel.
  • ProcessCmcIpmiMsg plus ChannelDecodeIPMBMsg: the queued object is not cleared; the decoder writes header fields and memcpy's only the declared payload, leaving the remaining tail uninitialized/stale.

Required proof: Reproduce the selector 0x02/0x12 license decision with a controlled long-request/short-request KCS sequence before assigning an authorization-bypass impact, and confirm the initialized KCS channel in the tested runtime uses the statically identified polling thread. Separately determine whether the modular CMC producer is active and externally reachable on this platform.
